# incident-audit

journal 的失败模式不是「写错」，是**静默退化**：数字过期、status 虚高、同一类错误反复出现却没人发现。

这个技能扫一遍，只报告，**不自动改**。

## 先定位库

读 `~/.dsh/incident-journal.yml` 拿 `journal_root`。
不存在或没有 `journal_root` → 报告「库未指定」，停。

条目在 `<库根>/<项目名>/坑/`、`<库根>/技术点/`、`<库根>/思想风格/` 三处。
索引是 `<库根>/README.md`、`career.log`、`REVIEW.md`，以及每个 `<项目名>/README.md`（项目视图，只存链接）。

## 八项检查

### 1. 索引是否完整

条目文件存在但**没进索引**？时间线缺行？`REVIEW.md` 里没有任何题指向它？`<项目名>/README.md` 没列它？

**漏一处等于没收录** —— 这个库一半的价值在索引上，因为索引是复习的入口。

`<项目名>/README.md` 里的链接**悬空**（指向不存在的文件）也要报 —— 它只存链接，链接坏了这一页就废了。
**「悬空」和「没收录」是两回事**：前者是索引指错了，后者是该指没指。

### 2. 反事实段是否存在

按 kind 查对应那一段在不在、是不是只写了 A 没写 B：

| kind | 该有的段 | 只写结论的样子 |
|---|---|---|
| `坑` | 我原来以为 | 「我以为 X」而没有「因为 Y」 |
| `技术点` | 没有它我会怎么做 | 「用了 X」而说不出不用会怎样 |
| `思想风格` | 约束边界 | 「他们这么做」而说不出什么时候不该这么做 |

缺的按主技能 `incident-journal` 的资格规则处理：删，或重写。**缺反事实的一律标 `[流水账]`。**

### 3. 数字是否退化

- 标了 `[推算]` 但后来实际跑过的 → 应该升级为 `[实测]`，补证据
- 标了 `[实测]` 但**没有命令或输出** → 降级，或补证据
- 数字**明显过期**（依赖的版本、外部服务的字段、价格）→ 标记为待复核

### 4. `[资料]` 有没有被写成事实

扫含 `[资料]` 的句子：是不是写成了「X 是这样」而不是「资料说 X」。
**带出处的错误比没出处的更可信**，这里的污染最重，发现就报。

同时检查 `## 与资料的关联` 引用的 `资料/<文件名>` 是否真的存在、行号是否还落在文件范围内。

### 5. 源码位置是否还可校验

`<repo> @ <commit> · <path>:<符号名>` 四样缺哪样：

- 没有符号名、只有行号 → 标 `[退化]`（行号会漂，而且不报错）
- 没有 `repo` / `commit`，而库和代码是两个仓库 → 标 `[退化]`
- 符号名在当前代码里已经不存在 → 标 `[过期]`

**位置是线索，不是链接。** 库和代码是两个仓库，行号漂移、符号名消失都是常态。
只有**本来能写上的那部分缺了**才报退化 —— 有 `repo` 可写却没写、有符号名可写却只写了行号。
正常的漂移不报，否则这份报告一半是噪声。

### 6. 重复模式

把条目按「可迁移判据」聚类，再按项目看：

- **同类 `坑` 出现在 3 个以上项目** → 它已经不是坑了。建议提成一条 `技术点` 或 `思想风格`，原来那些坑各自留在项目里，新条目把它们串起来。
- **同一判据的 `技术点` / `思想风格` 出现 3 次以上** → 说明规则没写清楚。那不是三条，是**一条规则的 bug**，建议加厚合并成一条，并补一节「为什么反复出现」。

库的划分是「`坑` 跟项目走、`技术点` / `思想风格` 跟人走」，这一项就是维持它的机制 ——
没有它，`坑/` 会无限堆积同一件事，而跨项目的那条判据永远沉淀不出来。

### 7. 三类是否严重失衡

全是 `坑`、`技术点` 和 `思想风格` 一条都没有 → 指出。
通常不是没发生，而是**门槛被误读成只管坑**。

### 8. 该记没记的坑

唯一需要推断的一项。看：

- `git log` 里 `fix` / `revert` / `hotfix` 类的提交，有没有对应条目
- `career.log` 里的事件，有没有引用不存在的 `of-NNNN` 编号
- **本次会话里**是否发生过「判断被推翻」但没落盘的时刻
- 有没有**该加厚却新建**的条目 —— 同一个技术点被拆成两条，各自只说了一半

## 输出格式

按严重度排序，每条一行：

```
[断链]   career.log:18 引用 of-0007，但没有任何条目定义它
[悬空]   项目视图 work-as-team/README.md 指向 技术点/xxx.md，该文件不存在
[流水账] 坑/foo.md 缺「我原来以为」；技术点/bar.md 说不出不用会怎样
[污染]   技术点/baz.md 把 [资料] 写成了事实：「Redis 是单线程的」（资料这么说，你没验过）
[退化]   坑/qux.md 只写了行号没写符号名；标 [实测] 但无证据
[重复]   a.md / b.md / c.md 共享同一判据「查不到被编码成合法值」→ 建议加厚合并
[提升]   坑/jwt-expiry-a.md、坑/jwt-expiry-b.md 分属两个项目、同一判据 → 建议提成一条 技术点
[失衡]   库里有 9 条坑、0 条技术点、0 条思想风格
[缺记]   commit abc1234 (revert: ...) 没有对应条目
[过期]   思想风格/x.md 引用的外部 API 字段名可能已变更（2026-04 核验）
```

最后给一句总结：**库现在能不能用**（索引完整 / 有多少条需要动手）。

## 不要做

- 不要自动改文件。报告完等对方决定。
- 不要把「条目写得短」当成问题。短而准 > 长而全。
- 不要因为 status 是 `已掌握` 就跳过检查 —— 虚高的 status 恰恰是退化最常见的表现，抽查 2–3 条，让对方当场复述。
