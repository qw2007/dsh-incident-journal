# 资格规则

这个文件的主要作用是把大部分东西挡在外面。

## 判据只有一条：能不能写出反事实

写不出来的，不管多有价值，不收。三类各自的反事实如下。

### 坑 —— 一个被推翻的判断

硬筛子：**「我原来以为 A，因为 B」**。B 必须存在。

- ✅ 「报错说『没有可用的凭据』，所以我以为要去登录账号；实际是 TLS 后端选错。」
  当时的你看到那段报错，会做出同样的推断吗？**会，才收。**
- ❌ 「我打错了一个字母。」—— 没有推断可言。

### 技术点 —— 一个值得留下的做法

硬筛子：**「没有它我会怎么做，错在哪」**。

- ✅ 「没有 `SKIP LOCKED` 我会用 `SELECT ... FOR UPDATE`，并发 worker 会互相阻塞。」
  —— 有一个具体的、我会真的采用、而且确实错的替代方案。
- ❌ 「今天我学了 Redis。」—— 写不出「没有它会怎样」。这是笔记，不是技术点。
- ❌ 「官方推荐的写法是 X。」—— 抄来的。你没有替代方案，也没有代价。

### 思想风格 —— 一个设计立场

硬筛子：**「它在什么约束下是对的，换什么条件就不对」**。

- ✅ 「用本地裸仓库当 origin，因为单机单用户；一旦有第二台机器或第二个人，就必须换成托管远端。」
- ❌ 「他们用了分层架构。」—— 这是描述，不是立场。没说出约束，也没说出它什么时候会错。
- ❌ 「我觉得这样很优雅。」—— 只有偏好，没有约束。

## 三类共用：还有三条

1. **有可核对的证据。** 数字、退出码、报错原文、命令输出。「感觉快了很多」不算。
2. **有代价。** 不知道会烧钱、丢数据、浪费几小时、或在生产中静默出错。「知道也无所谓」的不收。
3. **能迁移。** 换个项目、换门语言、换台机器还会撞上同一个模式。
   「这个库的 4.2 版本有个 bug」通常不迁移，除非它揭示的是一类接口设计问题。

## 明确不收

| 类型 | 为什么 |
|---|---|
| 语法错误、拼写错误 | 没有推断可言 |
| 装环境、配镜像、等下载 | 琐事，复现不了 |
| 网上抄来的标准做法 | 不是你的发现，没有反事实 |
| 没有数字的「最佳实践」 | 无法核对 |
| 含真实 Key / token / 账号 / 内网地址 | 安全红线，无论多有价值 |
| 「今天学了 X」 | 那是笔记，不是条目 |
| 只有偏好没有约束的「设计品味」 | 无法证伪，复习时也问不出东西 |

## 边界情况怎么判

**「我当时不知道，后来查到了」** —— 不算坑。
区别在于你当时**有没有根据手头证据做出推断**。有推断、推断错了，才收；纯空白，不收。

**「两个方案都行，我随便选了一个」** —— 不收（坑）。
有代价的取舍才收：「我选了 A 因为假设 QPS < 100，实测 3000，所以这个选择现在是错的。」

**技术点 / 思想风格的重复** —— **加厚**已有条目，不新建。
两步：①写之前先 grep（见主技能第三步）；②新点必须是**原条目没顾到**的 —— 新的边界、新的失效方式、新的约束。补进对应那一节，补上 `projects:`。
**边界：补到需要改标题，就不是加厚了** —— 那已经是原来那件事之外的另一件事，新建。
**原条目已经答上了这个点** —— 什么都不做，不要换个说法再写一遍。

**坑的重复** —— **从不加厚**。
坑对应单一项目、绑在一个代码位置上。同一个坑在第二个项目再踩，那就是第二个项目自己的新条目。
**但同类坑出现在 3 个以上项目时，它已经不是坑了** —— 那是一条技术点或思想风格，或者说明规则没写清楚。往上提这一步由 `incident-audit` 的「重复模式」检查负责；重复出现说明规则没写清楚，是规则的 bug，不是你的。

**一条同时像坑又像技术点** —— 按你**先意识到的那一面**归类。
先判断错了才学到做法 → `坑`；先看到做法才回头想「没它会怎样」→ `技术点`。
归错类不影响价值，只影响复习角度。

## 收进来之后

每条的 `status` 三选一：

| status | 含义 |
|---|---|
| `已掌握` | 能不看笔记复述原因和做法 |
| `需复习` | 记得结论，说不清原因 |
| `只见过一次` | 当时靠查资料解决，还没内化 |

`需复习` 和 `只见过一次` 是复习技能的输入。**只写不复习的笔记等于没写。**
