# 条目骨架

## 哪些节必须写

| 节 | 坑 | 技术点 | 思想风格 |
|---|---|---|---|
| 是什么 | ✓ | ✓ | ✓ |
| **反事实** | 我原来以为 | 没有它我会怎么做 | 约束边界 |
| **机制** | 真正的原因 | 它怎么工作 | 为什么这么设计 |
| 怎么定位的 | ✓ | — | — |
| 修法 / 怎么用 | ✓ 修法 | ✓ 怎么用 | — |
| 源码位置 | 涉及项目代码时必填 | 同左 | 同左 |
| 数字证据 | ✓ | ✓ | ✓ |
| 与资料的关联 | 命中资料才写 | 同左 | 同左 |
| 一句话怎么讲 | ✓ | ✓ | ✓ |
| 追问会问什么 | ✓ | ✓ | ✓ |

顺序有意义 —— 它走的是一条**从现象到可复述**的推理路径。

## 模板

```markdown
# <一句话结论，不是「关于 X」>

`kind: 技术点` · `of-0042` · `status: 需复习` · `projects: [work-as-team, driver-platform]`

## 是什么

原始证据：报错原文（整段，不要改写）、命令、日志尾部、配置片段。
读者要能拿这些自己复现。

## <反事实节：按上面表格三选一>

**你当时是怎么想的 / 没有它你会怎么做 / 它的边界在哪。**
这一段是整篇价值最高的地方 —— 三个月后你会忘记自己曾经这么想过。

写成「我以为 A，因为 B」。只写 A 不写 B，这段就没有价值。

## <机制节：按上面表格三选一>

机制层面的解释。不是「改成 X 就好了」，是「为什么会这样」。

## 怎么定位的        ← 坑

从现象走到原因的**路径**：试过什么、排除了什么、哪个观测把范围缩小的。
**把死胡同也写进来** —— 下次会更快排除。

## 修法 / 怎么用

具体命令或代码。可直接复制粘贴。

## 源码位置

`<repo>` @ `<commit sha 前 7 位>` · `<path>:<符号名>`（写入时在 `<path>:<行号>`）

```
（3–10 行关键原文）
```

## 数字证据

`[实测]` / `[推算]` / `[资料]` + 数值 + 证据位置（文件:行、命令、输出尾部）。

## 与资料的关联      ← 命中资料才写

`资料/<文件名>:<行>` · 它对上了哪一点 · 和你的实测一致还是有出入 · 面试官可能怎么追问。

## 一句话怎么讲

能对别人讲出口的一两句。这一节的存在是逼你把理解压到不用查笔记的程度。

## 追问会问什么

3–5 个问题，按「最可能被问到的」排序，附答案要点。
这一节直接喂给复习技能。
```

`projects:` 对 **技术点 / 思想风格必填** —— 它们在一级目录里跨项目共享，这是条目与项目之间唯一的关联。
`坑` 不用写，它本来就在 `<项目名>/坑/` 下。

**编号 `of-NNNN` 必须声明在文件里。** 它是索引（`career.log`、`README.md`、`REVIEW.md`）引用条目的句柄 ——
只写在索引里、不写在文件里的编号就是断链。两种声明方式，按「一个文件装几个实例」选：

- **一个文件一个实例** → 写在身份行上：`` `kind: 坑` · `of-0007` · `status: 需复习` ``
- **一个文件多个实例** → 每个实例一个 `## of-NNNN <子标题>` 小节，身份行不写编号

`incident-audit` 两处都认；两处都没有、却被索引引用的编号，报 `[断链]`。
单实例文件最容易断 —— 它的 H2 被语义节占满，编号没地方放，于是只活在索引里。

## 写作要求

**「是什么」抄原文，不要转述。**
> ❌ 报错提示凭据不可用，所以我以为是没登录。
> ✅ `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)`

转述会丢掉**误导性**——而误导性正是坑存在的理由。

**反事实段和机制段必须能对上。**
对不上说明你还没找到真因，这条先记成草稿。

**「怎么定位的」写过程，不写结论。**
结论在机制段里已经写了。这一节回答的是「下次怎么更快」。

**源码位置写符号名，行号只是辅助。**
`app/worker.py:142` 半年后指向的是一行注释，而且不报错。`app/worker.py:claim_task` 才找得到。

**位置是线索，不是链接。** 库和代码是两个仓库，行号漂移、符号名消失都是常态，
`incident-audit` 只在**本来能写上的那部分缺了**时才报退化，不报正常漂移。

**拿不到项目仓库标识就不要编。** 不在那个项目的工作区里时，`git remote` 和 `commit` 都拿不到 ——
写 `repo: 未知` 并标 `[推算]`。**编一个看起来像样的 commit sha，比空着糟糕得多。**

**加厚过的条目要留下痕迹。** 补进去的新点写清日期和来源项目，
例如「（2026-10-14 补，driver-platform：单机时不会暴露）」。否则三个月后你分不清哪句是当初的判断、哪句是后补的。

**没有项目代码就不要编。** 环境、机器配置、外部服务、一次性脚本的坑本来就没有源码位置，
写「无 —— 问题在 X」就行。**为了填满格子造一个位置，比空着糟糕得多。**

**数字必须可核对。**
`[实测]` = 你跑出来的，有命令或输出为证。
`[推算]` = 你算的、估的、从文档推的，**没跑过**。
`[资料]` = 来自 `资料/` 的外部信息，**不是你验证过的**。
宁可写 `[推算]` 也不要假装测过 —— 这份笔记的读者是三个月后的你，骗他等于骗自己。

**`[资料]` 绝不能写成事实。**
资料是二手信息，可能有错、可能过时。写法是「资料说 X」，不是「X」。
带出处的错误比没出处的更可信，所以这里的污染更严重。

## 长度

**一件事一篇。** 两个独立的坑不要塞进同一条。

**加厚的边界：** 只补「原条目没顾到、且删掉它原条目就不对」的点。
补到**需要改标题**，就该新建 —— 那已经不是原来那件事了。

典型长度 60–120 行。超过 200 行说明你要么在写教程，要么该拆了。

## 文件命名

`<slug>.md`，用小写连字符，描述**现象或判据**，不要用日期：

- ✅ `misleading-error-messages.md`、`host-scoped-blocking.md`
- ❌ `2026-10-11-bug.md`、`notes.md`

一个文件可以放**同一判据的多个实例**，每个实例一个 `## of-NNNN` 小节。
一个文件只有一个实例时，编号写在身份行上（见上）。

**编号让条目可以被时间线和复习题引用 —— 所以它必须落在文件里，不能只落在索引里。**
