# incident-journal

把值得留的东西沉成**可复习**的条目。三类：

| kind | 收什么 | 硬筛子（反事实） |
|---|---|---|
| `坑` | 一个被推翻的判断 | **我原来以为**什么，凭什么 |
| `技术点` | 一个值得留下的做法 | **没有它我会怎么做**，错在哪 |
| `思想风格` | 一个设计立场 | 它在**什么约束下**是对的，换什么条件不成立 |

**三类共用的唯一铁律：每条必须有一个反事实。** 没有反事实的条目 = 摘抄，不要写。

## 第一步：检查状态（每次先做）

读 `~/.dsh/incident-journal.yml`：

| 情况 | 动作 |
|---|---|
| 文件不存在，或没有 `journal_root` | 问用户库路径（**只问这一次**），写回文件 |
| 当前工作区不在 `active_workspaces` | **什么都不做**，只回一句「（journal 未启动，这次没记）」 |
| 在列表里 | 继续 |

**例外**：用户明确说「开始记录 / 停止记录 / 落盘」时，直接执行对应动作，不看 `active`。

```yaml
# ~/.dsh/incident-journal.yml
journal_root: D:\DSh\offer
active_workspaces:
  - D:\DSh\work-AS-team
```

## 第二步：确认够格

按 `references/qualifying.md` 判。不够格就不写 —— **那个文件的用处就是把大部分东西挡在外面**。

## 第三步：先查重，再决定加厚还是新建

**写之前必须 grep。** 不查重，「重复时加厚」这条规则永远不会真的触发 —— 你只有在已经想起来「我记过」的时候才会去加厚，而想得起来的时候你本来就不需要这条规则。

拿条目的标题、关键词、以及涉及的 `projects:`，去这四处分头 grep：

- `<库根>/README.md`（根索引）
- `<库根>/技术点/`、`<库根>/思想风格/`（跨项目共享，最可能已有）
- `<库根>/<项目名>/坑/`（本项目）

| 情况 | 动作 |
|---|---|
| 同主题条目已有，且**这次的新判断是它没顾到的**（新的边界、新的失效方式、新的约束） | **加厚** —— 补进对应那一节、补 `projects:`，**不新建文件** |
| 同主题条目已有，但它已经答上了这个点 | 什么都不做 |
| 新点自己就是一个完整反事实（「没有它我会怎么做」另有答案） | **新建** |
| `坑` | **从不加厚** |

**加厚到哪里停：** 只补「原条目没顾到、且删掉它原条目就不对」的点。补到**需要改标题** —— 也就是不再是原来那件事 —— 就该新建。一个文件往 500 行长，说明加厚变成了堆砌。

**为什么坑不加厚：** 坑绑在一个项目的代码位置上。同一个坑在第二个项目再踩，是那个项目自己的新条目；如果它在三个以上项目反复出现，那已经不是坑了，`incident-audit` 的重复模式检查会把它往上提成技术点或思想风格。

## 第四步：写条目

按 `references/skeleton.md` 落到对应目录：

| kind | 写到哪里 |
|---|---|
| `坑` | `<库根>/<项目名>/坑/<slug>.md` |
| `技术点` | `<库根>/技术点/<slug>.md` |
| `思想风格` | `<库根>/思想风格/<slug>.md` |

后两类**跨项目共享**，所以条目里必须有 `projects:` 一行写明它来自哪些项目 —— 那是条目与项目之间唯一的关联。

完整范例见 `references/examples/`。

写之前，拿条目的关键词 grep 一遍 `<库根>/资料/`；命中就在条目里加 `## 与资料的关联` 一节。

**写到 `<工作区>/.incident-journal-staging/`，不要直接写库根。** 库根在工作区之外，每写一个文件都要一次越权批准；暂存目录在工作区内，一次会话结束时 flush 一次即可。

## 第五步：同步四处索引

漏任何一处等于没收录：

- `<库根>/README.md` 加一行指针
- `<库根>/career.log` 加一行 `日期 | 事件 | 证据`
- `<库根>/REVIEW.md` 加 1–2 道自测题（答案用 `<details>` 折叠）
- `<库根>/<项目名>/README.md` 加一行 —— 技术点 / 思想风格按 `projects:` 标签聚合，链回一级目录

最后一处是**项目视图**：进到 `<项目名>/` 就能看全这个项目的三类条目。它只存链接、不存内容，所以指的东西永远是唯一的那份正文，不会出现「指针和正文不一致」。

## 库的固定布局

```
<库根>/
  资料/                        外部参考资料（面经、文档）
  技术点/                      跨项目共享 —— 跟人走
  思想风格/                    跨项目共享 —— 跟人走
  <项目名>/
    README.md                  该项目的条目清单（只存链接）
    坑/                        只属于这个项目
  README.md   career.log   REVIEW.md
```

`坑` 跟项目走，`技术点` / `思想风格` 跟人走。
布局是固定的，**不要为它造配置文件**。

## 铁律

- 每个数字标 `[实测]` / `[推算]` / `[资料]`；**没标的视为不可信**。
- **保留报错原文、命令、输出尾部。** 三个月后你要的是原文，不是你的转述。
- 写「我**凭什么**信了那个错答案」。错得有道理才值得记，手滑不值得。
- 源码位置写成 `repo @ commit · path:符号名`，写入时的行号附在后面。**符号名稳定、行号不稳定。**
- 位置是**线索**，不是链接：库和代码是两个仓库，漂移是常态。拿不到 `repo` 就写「未知」并标 `[推算]`，**不要编**。
- 加厚过的条目要留下痕迹：补进去的新点标出日期和来源项目。
- 条目里绝不出现真实 Key、token、账号、内网地址。
- 判据是「三个月后的自己能否看懂并复现」，不是「读起来漂亮」。

## 写完自检

- [ ] 反事实段真的有一个反事实（不是「我不小心」）
- [ ] 至少一个 `[实测]` 数字，或有明确证据路径
- [ ] 有可迁移判据 —— 换个项目还会遇到同一个模式吗
- [ ] 源码位置写了符号名，不只有行号
- [ ] 写之前 grep 过，确认这不是该加厚的已有条目
- [ ] 四处索引都动了
- [ ] 没有凭据泄漏
