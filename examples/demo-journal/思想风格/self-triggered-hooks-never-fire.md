# 把「什么时候该触发」交给正在做事的模型，等于不触发

`kind: 思想风格` · `of-0016` · `status: 需复习` · `projects: [work-as-team]`

## 是什么

`incident-journal` 这套技能的设计是：skill 的 description 里写触发词，**由模型在「发现值得记的东西」时主动调用 `skill` 工具**。宿主不挂任何钩子，插件只声明技能名和描述。

装好、同步进 `~/.dsh/skills/`、宿主当场就认了（技能目录里出现了 `incident-journal`）—— 然后**一次都没被调用过**。D1–D3 三个交付阶段全部做完，`offer` 库里的最新提交还停在 `7d61750`，比这段工作更早。

## 约束边界

**在什么约束下这个设计是对的：**

- 插件可以纯声明式安装，零运行时成本、不侵入别人的 agent 循环；
- 触发条件（「什么算值得记」）本身是模糊的，用自然语言描述比用布尔判断更准确；
- 用户习惯用斜杠手势显式点名。

**换什么条件就不成立：**

- 任务跨度长（一个目标要跑几十上百轮），模型全程「埋头做事」，注意力全在当前那一步上；
- 用户从不使用斜杠手势（这台机器上确实没有），触发只剩「模型自觉」一条路；
- 宿主本来就有 `agent/pre-step` 这类钩子 —— 那就应该在那里塞一句提醒，而不是指望模型想起来。

**核心判断**：**一个关于「什么时候做」的判断，交给正忙于别的事情的那一方，就等价于没有这个功能。** 它和「把错误处理交给调用方记得做」是同一类错误：规则是对的，但它永远不会发生。

## 为什么这么设计，以及它错在哪

动机是好的：不给宿主加钩子 = 插件可移植、可纯声明式安装、零运行时开销。代价被低估了 —— **「零运行时成本」在这里等于「零运行时存在」。**

而且失败是**静默**的，这是最坏的部分：

- 没有报错、没有日志、没有警告；
- 状态文件（`~/.dsh/incident-journal.yml` 的 `active_workspaces`）里当前工作区**在**列表里，所以从配置上看一切正常；
- 唯一能发现的判据是「库里有没有新文件」—— 而没有人会主动去数。

对比一下反面：如果它启动时报一句「journal 已启动」，至少会留下「我以为它在记」的痕迹。**响亮的失败比安静的缺席好，而最糟的是安静的成功声明。**

## 修法

把触发从「模型自觉」搬到「宿主每轮注入」。具体做法是往 `~/.dsh/AGENTS.md`（全局指令，每个会话都加载）加一段默认检查：

> 每轮开始前读 `~/.dsh/incident-journal.yml`；当前工作区在 `active_workspaces` 里时，检查上一轮是否推翻了某个判断、或学到了做法、或定了一个有约束的设计立场；有就调 `incident-journal` 技能。

关键点：**判据写进一个每轮都会被加载的文件**，而不是写进一个需要被想起来的技能描述。

## 一句话怎么讲

**「记得在 X 的时候做 Y」这种规则，只要 X 的识别依赖执行者本人的注意力，它就等于不存在。** 要让它存在，就得把判断挪到一个不会忘的调用方那里 —— 宿主钩子、每轮注入的指令、或者外部定时器。

## 追问会问什么

- 这不就是「文档写了没人看」吗？→ 更像「API 设计了但没人调」：机制是齐全的，缺的只是一个不会忘的调用方。
- 为什么不让技能自己更醒目一点？→ 醒目度对抗的是注意力，而注意力正是稀缺资源；结构性失败要用结构性办法修。
- 这个立场什么时候会反过来咬人？→ 每轮注入会占上下文、也会变成噪音；当任务本身很短、或用户明确不想被提醒时，宿主钩子反而比「模型自己判断」更糟。
