## 要点

### 12 道面试题（题目原文）

1. 为什么用 ES + BM25 混合检索？优化了多少，怎么测的，有多少人用？
2. 需求文档和代码文件通常很大，怎么保证检索正确？怎么判断对错？
3. 为什么要分成三层记忆？
4. 说说记忆设计，怎么保证长期记忆和外部记忆是正确的？
5. Plan-and-Execute 基于 DAG 拓扑排序，说说你的设计
6. Planner、Worker、Reviewer 的边界怎么设计？挂载的工具一样吗？
7. 如果子 Agent 还能调用子 Agent，怎么保证不会挤爆 Token？
8. 基模是什么？多个 Agent 的 system、user、assistant、tool 消息怎么编排，怎么保证不乱序？
9. 接入了几个工具？都是本地的，还是 MCP？
10. DOM 网页内容很大，怎么保证不撑爆上下文？
11. Transformer 的 QKV 和多头注意力机制
12. 算法题：最大无重复子串

### 面试者给出的实测数字（照抄，均为其自述）

- 用 **620 条真实 Query** 做标注：420 条调参数，200 条作为独立测试集
- 测试集上 Recall@10：BM25 **73.5%**，向量检索 **78.0%**，混合检索 **86.5%**
- P95 延迟从 **118 毫秒**增加到 **189 毫秒**
- 当时只是团队内测：激活用户 **74 人**，稳定周活约 **41 人**
- 检索结果的直接采用率从 **52.8%** 提升到 **64.6%**
- 面试者主动纠正术语：「ES + BM25」不严谨，实际是 ES 同时做 BM25 关键词召回和向量召回，再通过 RRF 融合

### 关键技术细节（照抄要点）

- 切分：需求文档按标题和段落切，代码按 AST 切到类和方法；每个 Chunk 保留文件路径、符号、分支、commit 等元数据
- 检索策略「小块命中，大块返回」：先召回小 Chunk，RRF 合并取 Top 30，再 Rerank 到 Top 6，放进上下文时用 `parent_id` 补回完整函数或需求章节
- 正确性分两层：检索层看标准片段是否出现在 Top-K（Recall@K、MRR）；任务层看 Agent 最后改的文件是否正确、测试是否通过，再加人工验收
- 硬过滤维度：`repo、branch、commit_id、权限`，每段证据带路径和行号
- 三层记忆：工作记忆（当前目标、DAG 状态、最近工具结果，任务结束压缩或清理）/ 长期记忆（用户偏好、仓库约定、历史经验，按需检索）/ 外部知识（需求平台、代码仓库、接口文档的实时事实）。三层冲突时以当前外部事实为准（例：长期记忆是 JDK 17，当前分支 `pom.xml` 已升到 JDK 21，以当前代码为准并把旧记忆标成过期）
- 记忆写入：抽取结构化 Memory Item，带来源、时间、作用域、置信度和证据；只有用户确认过的事实或工具验证过的结论才能进长期记忆，模型自己的一次推断不直接写入
- Planner 输出的不是自然语言步骤，而是结构化 DAG；节点含任务目标、依赖、输入输出、可用工具、Token 预算和超时时间；执行前检查节点重复、依赖存在、图中有无环；调度用 **Kahn 拓扑排序**，入度为 0 的节点进 ready queue；节点状态与产物做 checkpoint，失败不用全部重跑；发现计划有问题只重规划受影响的子图
- 角色权限：Planner 只看用户目标、仓库概要和工具说明，不能直接改文件；检索 Worker 只有只读工具，代码 Worker 才有工作区写入权限；Reviewer 能读需求、看 Diff、跑测试和静态检查，但原则上不能直接改代码；权限不写在 Prompt 里，而是在 **Tool Gateway 按角色和任务范围鉴权**
- 递归控制：默认禁止任意递归，只有指定节点能创建子 Agent，**最大深度 2**；整个任务有全局 Token 预算，父 Agent 派生子任务必须从自己的剩余额度里分配；**预算到 70% 后禁止继续派生**；父 Agent 只给子 Agent 最小任务包（目标、必要证据、工具、输出 Schema），子 Agent 只回摘要、关键证据和 Artifact ID；记录祖先链避免 A→B→A 的递归环
- 模型：主模型是私有部署的 **Qwen2.5-72B-Instruct**，通过 **vLLM** 提供接口；Planner 和 Reviewer 用 72B，检索改写、摘要这类简单 Worker 路由到 **14B**
- 工具数量：一共暴露 **11 个工具**，7 个本地（文件读取、关键词搜索、符号查询、Git Diff、Patch、沙箱测试等）+ 4 个通过 MCP 接入（需求文档、代码评审、Issue、内部知识库）；MCP 里 1 个本地 stdio Server、3 个走内网 Streamable HTTP
- 消息编排：每个 Agent 有独立 thread；System Prompt 含全局安全规则和角色边界，具体任务作为 user message；assistant 发起带 `tool_call_id` 的调用；并行事件带 `run_id、task_id、agent_id、seq_no、parent_event_id`，单个 Agent 内按 seq_no 保序，跨 Agent 按 DAG 依赖和 parent_event_id 判断因果
- DOM 处理：先删 script、style、广告、隐藏节点和重复导航，正文页用 Readability 提取主体，操作页只保留可交互元素；简化成 `node_id、role、name、state` 结构；工具单次最多返回 **4K Token**，单页累计最多 **12K**，超过分页；连续操作只传当前 viewport 和变化节点
- 注意力：`softmax(QK^T / sqrt(dk))V`，除以 `sqrt(dk)` 避免点积过大导致 Softmax 过于尖锐；多头把隐藏维度投影到多个子空间，最后拼接再经 `Wo` 投影；序列长度上的主要瓶颈仍是 O(n²)
- 算法题思路：滑动窗口，哈希表记录字符上次出现位置，`left` 一定要取 max；时间 O(n)，空间 O(字符集大小)

### 整理者总结的「这场一面真正卡人的地方」（照抄）

- 题目不偏，难的是面试官把每个项目名词往下追三层：**为什么做 → 怎么实现 → 怎么证明有效**
- 三个加分动作：发现术语不严谨就主动纠正；别只报最好看的数字（说清测试集怎么来、指标怎么定义、延迟代价、用户规模）；少说「保证正确」「绝对不会爆」，改成「我在哪些环节降低风险、触发什么阈值后如何降级、出了错能不能追溯」
