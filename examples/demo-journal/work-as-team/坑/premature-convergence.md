## 一句话

## of-0005 代理还没确认在跑，就想把代理写死

**status: 已掌握**

### 现象

`github.com:443` 直连探测失败（三次 False，各约 21 秒 `[实测]`），同时观察到系统代理是开着的：

```
ProxyEnable = 1
ProxyServer = 127.0.0.1:7897
```

`gh auth login` 报连接超时。

### 我原来以为

「系统代理开着」→ 「git/gh 也应该走代理」→ 那就先把配置固化下来：

```powershell
git config --global http.proxy http://127.0.0.1:7897
```

我向用户申请了写工作区外配置的权限。

### 真正的错误

**用户拒绝了，用户是对的。** 三条理由：

1. **前提没验证**：`7897` 根本没有监听，Clash Verge 没在运行。写进去的是一份指向空气的配置。
2. **配置是持久的**：这一写会把以后**所有** git 操作绑到一个可能不开的端口上。
3. **后来实测证明它会主动破坏正确路径**：

| 情况 | 结果 |
|---|---|
| 默认（直连） | `git ls-remote` exit=0，1337 ms `[实测]` |
| 强制指向已关闭的代理 | `git ls-remote` exit=128，2094 ms `[实测]` |

也就是说，我准备做的那一步，会把一条**本来能用的路径**变成失败。

### 真正的做法

**先验证，再固化；能临时就不要写全局。**

```powershell
# 1. 先确认代理在听
Test-NetConnection 127.0.0.1 -Port 7897 -InformationLevel Quiet   # 要 True

# 2. 确认直连通不通
Test-NetConnection github.com -Port 443 -InformationLevel Quiet

# 3. 只在需要时，为这一次会话临时设
$env:HTTPS_PROXY = "http://127.0.0.1:7897"
gh auth login --hostname github.com --git-protocol https --web

# 4. 登录成功后再固化 git 的协议行为
gh auth setup-git
```

### 我承认的另一个错

在那之前，我还把一次**成功的单次 TCP 探测**当成了「网络稳定可达」，并据此给出结论。同一个毛病的更早一次发作：**用一次样本推断一个会波动的状态**。

### 数字证据

| 项 | 值 |
|---|---|
| `github.com:443` 直连探测 | 三次 `False`，各约 21 秒 `[实测]` |
| `git ls-remote`（默认直连） | exit=0，1337 ms `[实测]` |
| `git ls-remote`（强制指向已关闭的代理） | exit=128，2094 ms `[实测]` |

### 追问会问什么

- 为什么用户拒绝权限申请是对的？→ 因为被申请的操作**前提不成立**；权限本身没错，错在时机。
- 怎么避免？→ 申请越权操作之前，先确认这次操作依赖的前提**可验证且已验证**。
- 「临时环境变量」为什么更安全？→ 它随会话消失，不会在模态切换后留下一个错误的持久状态。

## of-0006 砍「太重」的系统时，砍错了对象

**status: 已掌握**

### 现象

一份需求规格里把同一个系统描述成了约 90 个并列的方框 `[实测]`（控制层 11 个、监控 8 个、文档 8 个、门禁 10 个、阶段与子步骤若干）。按字面实现 = 约 6–12 人月 `[推算]`，而约束是「一个学生 + 月预算 $60–80 `[推算]`」。

### 我原来以为

系统太重 → **砍掉功能**。我给出 11 条削减：

- 删 Redis + Celery（用 Postgres 一张表当队列）
- 删「监控告警 Agent」（它就是 SQL 视图 + cron）
- 删 11 个控制层服务（都是 Router 函数）
- 删「每 Agent 独立容器 / 独立 Key」
- 删三个「假 Agent」（文档 = 渲染，部署 = shell 脚本，QA 评审 = 一次 LLM 调用）
- 删 Web 控制台 v1、删自然语言排程、删 CrewAI + AutoGen
- 删模板层直到有第二个真实项目
- 删 8 份文档，只留一张 `artifacts` 表
- 把质量门禁提到 P0

### 用户的纠正（原话要点）

> 「缩减之后功能极大缩小了，而且其展示上欠缺……核心目的还是完成一开始流程图中的所有功能，至于服务器配置的问题，一开始为 4 核(vCPU) 8GiB」

**功能面不许砍，展示要加强，而且要能在 4C8G 上跑** —— 机器规格 4 vCPU / 8 GiB `[实测]`（用户给定的约束）。

### 真正的原因

**我砍错了对象。该砍的是「实现重量」，不是「功能」。**

正确的换算规则是：流程图里**每一个盒子都保留**，但它从「一个服务」降级为「**一个纯函数 + 一行配置 + 一张自动生成的卡片**」。

| 原来（重） | 换成（轻） |
|---|---|
| 一个微服务/容器 | 一个纯函数（5–20 行） `[推算]` |
| 一张自建表 | 一行注册表记录 |
| 一个独立后台进程 | 一个 SQL 视图 + 一个 cron 任务（复用已有 worker） |
| 一个自定义 dashboard | 一张自动生成的卡片 |
| 一套自定义文档模板 | 一个 `kind` 值 |

结果：**功能面 100% 保留，进程数从 30+ 压到 1** `[推算]`。

关键手法是引入一张**组件注册表**（`registry.py`）：控制台的卡片、监控的指标、审计的账本全部从它派生，加一个功能 = 加一条记录。流程图和 UI 从**同一份注册表**长出，所以展示和实现不会脱节。

被真正降级的只有**形态**，不是功能：

- 自建 Langfuse → 云免费版或自建 `spans` 表（v3 需要 ClickHouse + Redis + MinIO，最低约 4 GB `[推算]`，直接吃光余量）
- Prometheus + Grafana（约 0.5–1 GB `[推算]`）→ 控制台直接查 Postgres 视图（0 MB），需要时用 `--profile observability` 一条命令加回
- 每 Agent 独立镜像 + 常驻容器 → **一个镜像** + 容器按需启停 + git worktree 做隔离

### 教训

「这个系统太重了」这句话里，**「重」可以指三件不同的事**：

1. **功能太多** → 砍功能
2. **实现太重** → 同一份功能换更轻的实现
3. **画得太细** → 把清单当结构了（把小函数、SQL 查询、同一张表的不同行都画成并列节点）

我默认选了 1，用户要的是 2（顺带修 3）。**动手削减之前必须先问：砍的是功能，还是实现？** 这两个的答案完全相反。

### 数字证据

| 项 | 值 |
|---|---|
| 需求规格里的并列方框 | 约 90 个（控制层 11、监控 8、文档 8、门禁 10，其余为阶段与子步骤） `[实测]` |
| 按字面实现的工程量 | 约 6–12 人月 `[推算]` |
| 约束：一个学生 + 月预算 | $60–80 `[推算]` |
| 目标机规格 | 4 vCPU / 8 GiB `[实测]`（用户给定） |
| 一个微服务/容器 → 一个纯函数 | 5–20 行 `[推算]` |
| 进程数 | 30+ → 1 `[推算]` |
| 自建 Langfuse v3 的最低内存 | 约 4 GB `[推算]` |
| Prometheus + Grafana 常驻 | 约 0.5–1 GB `[推算]` |

### 追问会问什么

- 为什么不砍功能反而是对的？→ 因为这是要长期生长的系统；功能面砍掉以后要补回来，成本高于一开始就用轻实现。
- 一个进程怎么承载 30+ 个「服务」？→ 它们本来就不是服务；判定标准和可用性要求都不同。用一张 Postgres 表 + `SELECT … FOR UPDATE SKIP LOCKED` 就是队列，不需要 Redis + Celery。
- 注册表为什么是关键？→ 它让「展示」和「实现」共享一个事实来源，避免两边各维护一份清单后逐渐脱节。
- 什么情况下该砍功能？→ 当这个功能**不属于核心目标**时。这里核心目标（跑通整张流程图）明确包含所有盒子，所以一个都不能砍。
